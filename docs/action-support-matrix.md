# Workflow action support matrix

This matrix documents the current on-disk implementation under `src/SPNet.Workflow.WfSerializer/` and `src/SPNet.Workflow.Publisher.Csom/`. Visible editor tabs may reference older `Core`, `Cli`, or `SharePoint` projects, but those projects are not present in this workspace snapshot or in `SPNet.slnx`.

Raw WF language expression activities are forbidden in generated/published SharePoint workflow XAML. Do not emit `VisualBasicValue`, `VisualBasicReference`, `CSharpValue`, or `CSharpReference`: they require VB/C# compilation and are rejected by SharePoint Workflow Manager validation (a raw `Microsoft.CSharp.Activities.CSharpValue<TResult>` publish probe failed as an invalid type). Builders must prefer structured SharePoint Designer/Workflow Manager-safe nodes such as SharePoint proxy activities and `Microsoft.Activities.Expressions` proxy expression activities. Exporter recognition of raw VB expression text is legacy/downloaded-XAML compatibility only and must not be treated as permission to generate those nodes.

YAML remains the authoring source of truth. Build output is the generated XAML plus a generated `*.xaml.metadata.json` sidecar. That metadata JSON is the normal publish contract for workflow display name/technical name/description, target, start options, initiation settings, and form fields. Legacy `*.xaml.formfield.xml` is compatibility/inspection output and an explicit deprecated fallback only; it is not the normal YAML publish input.

## Export parity notes

`ExportWorkflowYaml` is a lightweight structural export for diagnostics, not a full XAML-to-YAML round trip. It recognizes direct SharePoint child activities that are already supported by YAML-to-XAML and now has reference-backed recognition for common generated/reference XAML shapes including `Comment`, delays, `SetField`, list lifecycle actions, `Email`, `CallHTTPWebService`, `SingleTask`, plain WF `Assign`, WF `While`/`If` containers, generated numeric/string/Boolean/DateTime/DynamicValue comparison expressions, nested `and`/`or`/`not` condition trees, `parseDate`, `parseDynamicValue`, generated string-manipulation expression activities for `ReplaceString`, `Substring`, and `Trim`, and narrowly recognized nested lookup expression activities. The exporter preserves supported nested actions under `while`/`if`, normalizes SharePoint Designer-local DateTime operands to UTC, retains condition/expression Designer `Id` values as `designerId` when required for RHS operand rendering, and emits buildable placeholder comparison conditions when it cannot reconstruct the exact condition safely. Expressions, recipients, list IDs, identities, and operands are intentionally placeholdered unless represented as simple attributes, simple literals/variables, or narrowly recognized generated/VB expression text such as current-list/current-item/context/list-item lookups. Most generated workflows are wrapped in SharePoint Designer stage metadata, nested WF `InArgument` expressions, and proxy-specific activity shapes; adding robust export for the full action surface requires either WF deserialization with the local WebsiteCache proxy assemblies or more detailed proxy metadata than this repository can safely assume. Export warnings remain explicit so partial diagnostic output is not mistaken for authoritative round-trip YAML.

## SharePoint Designer conditional metadata notes

The `ExampleConditionals` round-trip showed that publish validation and Designer rendering are separate compatibility bars. A generated condition tree can validate and publish while Designer still displays `(insert a condition)` or blank RHS operands if the expression metadata is not Designer-compatible. Keep these rules when changing condition builders/exporters:

- Boolean condition and operand conversion expression nodes need SPD-compatible `Result="{x:Null}"` plus the expected Designer custom attributes.
- `ParseDate.CultureName` should remain the SharePoint Designer property-element shape that calls `GetConfigurationValue`; do not flatten it to a plain culture attribute when preserving SPD-authored conditions.
- RHS `ArgumentValue` condition operands need `ArgumentValue.Result` / `OutArgument` wrappers for Designer token rendering.
- Nested RHS conversions such as `ParseDate` and `ParseDynamicValue` may need the original Designer `Id` GUID preserved through YAML as `designerId`; the live `ExampleConditionalsRoundTripPreserveIds4` validation confirmed missing RHS values became visible after preserving those IDs.
- SharePoint expression proxy namespaces should use the SPD/publish-compatible non-assembly namespace form.

Any mention of VB expression text in export support means legacy/import compatibility only. New builders and generated XAML must continue to emit structured activity nodes and must reject raw VB/C# WF language expression activities before publishing.

## Adding a new action checklist

Keep action additions narrow and make each supported action explicit across the YAML, build, export, and test surfaces:

- Add or extend the YAML model in `YamlWorkflowModel.cs`, including a stable canonical `Type` value and any safe aliases in `WorkflowActionYamlTypeConverter`.
- Add validation near the model for required fields, safe top-level versus nested-expression usage, and any allow-lists that prevent unsupported Designer/runtime shapes.
- Update `WorkflowVariableTypeInferer` when the action writes to workflow variables or requires implicit infrastructure variables.
- Implement the activity builder in the appropriate file under `Actions/`, reusing `WorkflowExpressionBuilder` and preserving existing expression behavior.
- Do not implement builders with raw WF language expression activities (`VisualBasicValue`, `VisualBasicReference`, `CSharpValue`, or `CSharpReference`). Use structured SharePoint proxy or `Microsoft.Activities.Expressions` nodes and add tests/guards proving the generated XAML avoids raw language expression types.
- Keep publish metadata in YAML and ensure the effective metadata sidecar `*.xaml.metadata.json` remains authoritative for display name, technical name, description, target, start options, initiation settings, and form fields. Do not add a normal publish dependency on `*.xaml.formfield.xml`; FormField XML must remain deprecated fallback/compatibility output only.
- Register the action model type in `WfActivityBuilderSerializer.CreateActionBuilders()` so dispatch is explicit and discoverable.
- Decide whether the action is valid as a nested expression, a stage action, or both; document and test the expression behavior.
- For condition/expression builders, preserve Designer-compatible metadata shapes (`Result`, custom attributes, property-element configuration values, `ArgumentValue.Result` wrappers, `designerId` when exported) before treating publish validation as sufficient.
- Update `WorkflowYamlExporter` only if structural export can recognize the action safely; otherwise mark export as unsupported in this matrix.
- Add or update tests for aliases/model conversion, validation failures, build-dispatch registration, variable inference, and export recognition when applicable.
- Add a safe sample YAML file or extend an existing sample only when the action can be demonstrated without live side effects.
- Add or update the support-matrix row with aliases, builder status, export status, sample/test coverage, validation status, risk, and caveats.
